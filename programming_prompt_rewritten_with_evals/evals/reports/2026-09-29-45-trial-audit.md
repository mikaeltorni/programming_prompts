**This trial is not fully compliant**, even if the workflow prose rule is

## Why the existing defenses did not catch these cases

The current judge prompts already instruct the model to align its yes/no
score with its final reasoning, preserve “and may” clauses, check source
boundaries, and use the evidence helper before a logging no. Repeating those
requirements does not explain away these failures: the judge disobeyed them.

The runtime has a reliability gate in
[`llm_judge/reliability.py`](../verifier/llm_judge/reliability.py), which retries
unsupported judgments rather than awarding a pass. Replaying that gate on
the actual bank-commits, bank-logging, and stats-commits rows returns `None`
for all three: it considers their no verdicts usable.

- The explicit contradiction regex does not recognize the bank's concluding
  “No feature-boundary violation found” or the stats explanation's allowed
  follow-up conclusion. A valid-looking mapping is not itself a generic
  syntactic proof, so the latter requires semantic review.
- The logging source-conflict regex recognizes `fallthrough`, but the actual
  reason says `fall-through`. It also puts the later “no return” wording
  beyond the expression's same-line, bounded claim match. The final return
  therefore never triggers that source-conflict defense.
- The skip-inspection detector does not match the statement that the required
  helper check “was not run.” The verdict survives despite admitting omission
  of its mandated evidence check.

The raw embedded judge output has the same no scores as the reward rows.
This is an evaluation-model/reliability issue, not archive-summary arithmetic.
The workflow false positives further show that negative-only reliability
checks cannot establish that passing explanations counted source sentences
correctly.

## Recommended changes, with their boundaries

1. **Keep the behavior and Feature boundaries unchanged.** The replays do not
   justify splitting multiply/divide or median/reset, adding artificial
   commits, adding a None trace to `_assets`, or restoring task markers.
2. **Repair the judge reliability path with bounded evidence.** Normalize
   claim spelling for source-conflict checks and treat admitted omission of a
   mandatory helper as an unusable verdict. For a no with a passing conclusion,
   request a bounded independent reconsideration. If it remains unsupported,
   report an evaluation/missing-evidence failure; do not silently change no
   to yes based on a phrase. Retain both attempts and calibrate genuine no
   controls to avoid suppressing real failures.
3. **Make ledger ownership explicit between skills and judges.** Check source
   sentence fidelity, one sentence per row, and stale numeric claims against
   the actual request. Preserve the distinction between a legitimate optional
   follow-up commit and an illegitimate extra ledger Feature. The counter
   typo belongs to exact copying, not command correctness or phase order.
   Avoid task-specific Feature counts or command-token catalogs.
4. **Clarify the final Details contract.** If historical “next” wording is
   allowed, assess final statuses, observed order, and actual completion. If
   every Details cell must describe only the final state, put that requirement
   in both skill and judge. The calculator count contradiction is already
   expressly forbidden and needs consistent enforcement.
5. **Check delivery of changed documentation.** Existing worktree evidence
   proves some source commits used isolation, not that every artifact did.
   A tracked-file/history check can expose a live-only README without imposing
   a new workflow phase or conflating docs content with Git delivery.

These are proposed corrections, not claims of a verified runtime repair.
Implementing runtime changes would require the project's baseline and positive
Harbor smoke jobs for each coding harness, all with `--eval-agent codex`,
plus inspection of archived results. Prompt changes need focused real-judge
calibration against these valid and invalid submissions. This investigation
made only report/README edits, so it did not run a new paid benchmark or modify
installed skills or desktop state.
